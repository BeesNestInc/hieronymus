# 明細取込

銀行通帳・カード利用明細をファイルで取り込み、既存の仕訳と突合して、未照合の行から仕訳伝票を一括起票する機能です。取り込んだ明細は、[通帳元帳](ledger.md#通帳元帳)の入出金履歴と突合されます。

## できること

| 種別 | 形式 | 入口 | 処理 |
|---|---|---|---|
| 銀行通帳 | Excel(.xlsx)/CSV/画像 | 通帳元帳 →「明細取込」 | 既存仕訳と突合 → 未照合行を一括起票 |
| 社用カード明細 | PDF（Web明細の印刷） | 通帳元帳 →「明細取込」 | 利用行ごとに経費起票（貸方=未払金カード） |
| 個人カード明細 | Excel/CSV/画像/PDF | 精算書入力 →「カード明細から取込」 | チェックした行を精算書の明細に追加 |
| **計算書（ECモール等）** | PDF（CSV） | 通帳元帳 →「明細取込」 | **計算書1通 → 複合伝票1枚**（下記「計算書の取り込み」） |

## 取り込みの流れ

1. 「取り込む」で通帳と、順に取込ファイルを指定します
2. 内容確認でパース結果（行数・期間・警告）を表示します。銀行系は残高整合（前残+入金-出金=次残）を検証し、崩れがあれば警告します
3. 「取り込む」で明細が登録されます

## 突合と起票（銀行通帳）
1. 「既存仕訳と突合」ボタンで、取り込んだ通帳の仕訳明細と照合します
   * 金額が一致し、伝票日期が前後3日以内の明細を対応付けます
2. 「一括起票」で未照合の行を起票します（行ごとに1枚の伝票。承認待ち）
   * 相手方は、**学習ルール**（摘要 → 相手方仕訳）に従って決まります
   * ルールに該当しない行は、**仮入科目**（出金仮 1900000 / 入金仮 3900000）で起票されます（状態は「仮起票」バッジ）
   * **手数料の行は、前の行（同じ日）の伝票に合流します**（振込の次の行の振込手数料、ATM出金の次の行のATM手数料など）。合流させる摘要は**完全一致**で判定し、通帳共通の「お約束」として `libs/bank-reconcile.js` の `MERGE_DESCRIPTIONS` に定義します（表現の揺れは列挙する。通帳ごとの設定は不要。前の行がなければ/日付が違えば自分の伝票になります）
   * **利息行は自動でテンプレ仕訳になります**: 借方 普通預金（税引後）+ 借方 源泉所得税 / 貸方 受取利息（税抜）。源泉額が丸め0円の極小額は受取利息のみ
   * **同じ日の次の行に「国税」明細行**（category=tax）**が来る通帳**では、その出金額を源泉徴収額として採用します。この場合利息行の金額は税込（総額）扱いなので、普通預金の借方は「利息額−源泉額」となり、国税行は利息の伝票に合流します。国税行が無い（または額が大きくて納税の振替と判断される）場合は既定の源泉徴収率で逆算し、国税行は従来どおり仮入科目で起票します
3. **「後の処理」**（完全自動）: 仮起票した伝票は、後から入力された実科目の伝票（請求書・領収書など。金額一致+日付±3日）と突合して、仮科目を正しい科目に差し替えます。同時にその摘要と科目のルールを学習します
4. 「再実行」ボタンで、未承認の起票伝票を解放して現行ルールで作り直します（確定済み伝票・精算書由来伝票・会計年度確定中の伝票には触りません）
5. 対象外にしたい行は「対象外にする」で除外できます

## 学習ルール

* 「学習ルール」ボタンで一覧・編集・削除ができます
* ルールは「通帳+正規化済み摘要（NFKC・空白潰し・完全一致）→ 相手方科目（+補助）」です
* **ルールには方向（出金/入金）があります**: 方向はユーザーが選ぶものではなく、**取り込行の出金/入金フィールドに金額があるかで導出されます**（摘要クリックから登録すると自動で付く）。同じ摘要でも代理店的な取引先では入金と出金で相手方が違うことがあるため、**入金ルールと出金ルールは別のルール**として登録します（方向の変更は「削除→正しい方向の行から再登録」）
* **貸方の指定（任意）は出金ルール専用**: 通常は空で、貸方=通帳の勘定科目（未払金・普通預金等）で起票します。キャッシングリボのように貸方が短期借入金になる特殊行は、貸方を指定してください（フォームには通帳の科目が既定値として見えています）。入金ルールでは貸方=相手方そのものなので指定欄は出ません
* 通帳の勘定科目を後から変更しても、**貸方を指定したルールはその値のまま追従しません**（変更する場合はルールを直してください）
* ルールは「隙あらば学習」します: 実科目で起票した伝票（手作業修正、後の処理による差し替えを含む）から蓄積します
* ルールは実科目だけを指します（仮入科目は相手方になりません）
* テーブル行（明細行）の「学習ルール追加」ボタンから、その行の摘要でルールを手登録できます

## 社用カード明細（PDF）

カードWeb明細の印刷PDFを取り込むと、利用行ごとに経費起票します。

* 借方=支払先マッピング（利用店名からの候補提示）、貸方=未払金（カード）
* 取り込んだPDF本体は「明細取込」の記録に保持され、画面から参照できます
* 銀行側の引落行（摘要にカード名を含む行）は、カード明細の支払総額・支払日と照合したうえで、「借方 未払金 / 貸方 普通預金」の決済伝票を起票します

## 計算書の取り込み（ECモール等の支払明細）

ECモール（Amazon等）は「売上から広告費・手数料を差し引いて振込みます」形式の**計算書**を月次で発行します。計算書は**振込1本の内訳書**なので、**計算書1通を複合伝票1枚に起票**します:

1. 通帳の種類に「計算書（ECモール等）」を選び、Amazon等の名前で通帳を追加します
2. 計算書ファイル（PDF/CSV）を取り込むと、全行が**売上側 / 費用側 / 振込行**に分類され、集計（売上合計 = 振込 + 費用合計）の検算が表示されます。**Amazonの支払明細書のようにテキスト層のあるPDFは決定的に解析します**（AI読取不要・無料・毎回同じ結果。テキスト層のないPDFは画像化してAI読取します）。分類の語はプロファイル（`config/banks/*.yaml` の `type: settlement`。`salePattern`/`transferPattern`）で調整します
3. 費用行ごとに科目を選びます（学習ルール → 候補提示。ラベル→科目は計算書の通帳ごとに学習される）。**集計行と内訳が両方載る計算書**（Amazonの支払明細書は「FBA 1,447」とその内訳「納品895+在庫保管552」が並んで載る）では、チェックを外して重複の方を除外します。**選択した行の合計で検算が合うときだけ起票できます**
4.「1伝票にして起票」で複合伝票を起票します（承認待ち）:

```
借方: 入金先預金（振込額）+ 費用各行（広告費/支払手数料/FBA等）
貸方: 売上高（売上側の合算。商品代金・税金・配送料を含む税込の合算）
```

* 貸借は必ず一致します（売上合計 = 振込 + 費用合計の復路）。検算が合わないときは起票できません
* 税は全行0で入っています（売上高への税込合算の運用向け。消費税の分離が必要な書式が出てきたらプロファイル側で拡張する）
* 取り込んだ計算書本体は明細取込の記録に保持され、画面から参照できます

**通帳との紐付けと自動統合**: 振込で入る行は複合伝票で既に借方が経っています。Amazon振込の入った通帳（銀行通帳）を開くと、金額が一致し日付±3日の計算書複合伝票の候補が行に表示されます：

* **通帳側がまだ未処理**のときは、「計算書と突合」で紐付けます（該当伝票は**増えず**、行は照合済になります）
* **通帳側に「入金仮」の仮伝票が既にある**ときは（「一括起票」で仮起票した後）、計算書を起票するタイミングで両者は**自動で1本に統合**されます（下記「同じ取引の伝票を1本にまとめる」）。二重計上を防ぐための蛇口です

## 同じ取引の伝票を1本にまとめる（自動統合）

明細取り込みは「通帳・カードの行から起票した伝票」と「計算書・精算書から起票した伝票」が
**同じ取引**になることがあります（送金のタイムラグや精算の支払日との差で、日付が数日ずれる）。
それぞれの伝票が起票されるタイミングで、両者が同じ取引だと分かる場合に自動で1本にまとめて
二重計上を防ぎます。仕様の詳細は[伝票統合の仕様](../Docs/bank-statement-merge.md)を参照してください。

### 計算書 ↔ 「入金仮」の伝票（入金側）

* 計算書を起票したとき、同じ銀行科目・同じ金額で、日付が±3日以内の**未承認の「入金仮」伝票**がちょうど1つある場合は、計算書側の中身がその伝票に**統合**されます（トーストで「同じ取引の通帳側伝票に統合しました」と出ます）
* 残るのは**通帳側の伝票**です。伝票番号・日付（実際の入金日）・通帳行の紐付けがそのまま生きます。統合後の内容は「借: 銀行科目（振込額）/ 貸: 売上高（計算書の貸方）」+ 計算書の費用行が加わった1枚の複合伝票です
* 統合候補が無い・複数あるときは、従来どおり計算書側の伝票が作られます。その場合は計算書の画面に**「入金仮伝票と統合」**ボタンが出るので、そこから手動で統合できます（候補の未承認伝票を選んで統合。計算書側の伝票は破棄されます）
* 統合が効くのは**両方未承認**のときだけです（承認済みの伝票には触りません）
* 計算書側の伝票が実通帳の入金行に紐付いていない場合は候補になりません（計算書同士の突合はしません）

### 精算書 ↔ 「出金仮」の伝票（出金側）

* 経費精算書の承認で起票した伝票（借: 費用 / 貸: 出金元のカード）と、カード取り込んだ明細から仮起票された伝票（借: 出金仮 / 貸: その出金元）が、出金元と金額（合計）が一致し日付±3日で**1組だけ**対応するとき、**カード行の突合先を精算書側の伝票に付け替えて、仮伝票は消えます**
* 残るのは**精算書側の伝票**です（借: 費用 / 貸: カードの完成形。伝票日付=精算書に入力した支払日）。カード明細ビューでは、その行は「起票済」のまま、精算書の伝票の明細に紐付きます
* 候補が複数ある・日付が超過する・仮伝票が承認済みのときは何もしません（伝票が重複したままになることがあります。重複した仮伝票と精算書伝票は、精算書の伝票を消す/再承認するか、仮伝票を「削除」して手動で整理してください）
* 立替精算（出金元=仮払金の精算）は対象外です。カード・口座取り込み行との統合が対象です
* 精算書側の伝票は承認済みでも対象にできます（内容を変えず、突合先の付け替えだけが起きるため）

### 条件のまとめ

| | 入金（計算書 ↔ 入金仮） | 出金（精算書 ↔ 出金仮） |
|---|---|---|
| 残る伝票 | 通帳側（実入金日の伝票） | 精算書側（支払日の伝票） |
| 消える伝票 | 計算書側の伝票 | カード側の仮伝票 |
| 金額 | 銀行側（預金借方）の一致 | 出金元（カード取り込み側）の合計一致 |
| 日付 | 伝票日付±3日 | 同じく±3日 |
| 承認 | 両方未承認 | 仮伝票が未承認（精算書側は承認済みでも可） |

## 個人カードの立替精算

立替払いで個人カードを使った場合、精算対象は明細の一部（メモ等で印を付けた行）です。

1. 精算書入力画面の「カード明細から取込」で個人カードの明細を取り込みます
2. 精算対象の行にチェックを付け（メモ欄の記載がある行は既定でチェック）、支払先を選んで「精算書に追加」します
3. 追加された行は通常の精算明細と同じフロー（保存→承認→起票）で処理されます

## 取り込める形式

* Excel(.xlsx): 列名（日付/内容/出金金額/入金金額/残高/メモ等）を自動名寄せします。「出金金額(円)」のような括弧付き単位も扱えます
* CSV: UTF-8のみ
* 画像(PNG/JPEG): AI（LLM）で読み取ります。AI未設定環境では取り込めません
* カード明細PDF: テキスト層のあるWeb明細の印刷PDFに対応します。**テキスト層が実質ないPDF**（本文が字形描画で数字だけのエポスカード明細書など）は、画像化してAI読取にフォールバックします
* 計算書PDF: テキスト層が無い計算書は画像化してAI読取にフォールバックします（Amazon計算書はこの形）

## 書式の学習（AIプロファイル起草）

新しい書式が出てきても、コードを直さなくてよい仕組みです。プレビューで読めた書式を、次回から「決定的に」解析できるyamlプロファイル（`config/banks/*.yaml`）として学習します。

* **どの環境でも最初から動く**のが基本です（プロファイルが空でも、既定の解析とAI読取で取り込めます）。プロファイルは各環境のローカル設定（口座の約束科目などを含むため、配布物には含めません）
* **計算書（type: settlement）も学習対象です**: テキスト層のある計算書PDFは決定的解析（detect/集計行/振込行のパターン）まで学習できます。テキスト層のない計算書は、AI読取の分類と約束科目に使う「分類プロファイル」として保存します（テキスト層のある月の計算書で再度起草すると、決定的解析まで学習できます）
* **エポスカードなど「テキスト層が実質ないPDF」はプロファイル保存が必須**です（保存しないと来月もまた毎回AI読取（数十秒+コスト）。保存すれば次回から即時・無料・AI不要）
* JCBカードのように汎用パーサーで読める書式は、保存しなくても動きます（保存しておくと将来の様式変化にも対応しやすくなる）

1. 取り込みモーダル「内容確認」でプレビューが出たら **「この書式を学習する」** を開きます（会計権限+AI設定のある環境でだけ表示）
2. **「プロファイルを起草」**: AIが対象書式のyamlを書き、**同じファイルをそのyamlで決定的に再解析してAI読取と一緒かを自動検証します**
   * **検証OK**（緑バッジ）= 「日付+金額」でAIの読みと全行一致する書式の学習ができました
   * **相違あり** = 一致数/行数が分かるので、yamlを編集して納得いくまで試せます（相違のあるyamlは保存しないのを推奨します）
3. **yamlは編集可能**（textareaに表示されます）: AIの出した正規表現に不備があれば直してから保存してください（AIはtotal/payDateの正規表現を省略することがあります。その場合も行の読取に支障はありませんが、銀行側の引落照合に使うなら補ってください）
4. **「プロファイルを保存」** → `config/banks/<名前>.yaml` に置かれます（保存前にyamlの検証ゲート。壊れたyamlは書きません）
5. 次回以降の同じ書式の取り込みは、プロファイルで決定的に解析されます（AI読取は不要）

* プロファイルは書式ごとに1つずつ蓄えます（書式が増えるたびにyamlが増える。コードは直さない）
* 起草できるのはテキスト層のある書式（PDF/Excel/CSV）だけです（画像は学習対象外）

## 設定

取り込む銀行・カードの形式差は `config/banks/*.yaml` のプロファイルで調整できます（前節の「書式の学習」でAIに起草させることもできます）。

```yaml
name: 三井住友カード
type: card                  # bank | card
detect:                     # ヘッダ署名（Excel/CSVの自動判定用）
  - 日付
columns:                    # 列名 → 項目（省略時は既定の名寄せ表）
  date: 取引日
categoryRules:              # 摘要パターン → 区分（省略時は既定ルール）
  - { pattern: '^利息', category: interest }
cardPatterns:               # カードPDF用の正規表現（省略時は既定パターン）
  total: '支払い合計額([\d,]+)円'
paymentAccount: '3020000'   # 引落決済の借方科目（未払金）
paymentSubAccount: 1
interest:                   # 利息仕訳テンプレ（bank種別のみ）
  incomeAccount: '8000000'  # 受取利息
  account: '3730000'        # 源泉所得税の科目（省略時は補助「源泉」から自動解決）
  subAccount: 1
  rate: 0.15315             # 源泉徴収率（同じ日の「国税」行がないときの逆算に使う）
```
