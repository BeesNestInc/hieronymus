## 2025年10月25日 学習結果

### 1. Svelteのリアクティビティとオブジェクトの更新
- **教訓**: Svelteにおいて、`bind:` でプロパティを渡している場合でも、親コンポーネントでオブジェクト全体を再割り当て (`status = { ...status, fy: {...} }`) すると、子コンポーネントにリアクティビティが伝播しない場合がある。オブジェクトのプロパティを直接変更し、`status = status;` のように自己代入することで、Svelteに更新を検知させ、リアクティビティをトリガーできる。

### 2. `parseInt()` と `NaN` の挙動
- **教訓**: `parseInt(undefined)` は `NaN` を返す。`NaN > 0` は `false` となるため、条件分岐で意図しない `else` ブロックが実行される可能性がある。APIのパラメータとして `undefined` や `null` が渡される可能性がある場合は、`parseInt()` の前に適切なバリデーションやデフォルト値の設定が必要。

### 3. CSS `height` の `calc()` とレイアウト
- **教訓**: `height: calc(100vh - Xpx)` の `X` の値は、画面全体のUI要素の高さの合計を正確に把握する必要がある。特に、グラフのような動的な高さを持つ要素がある場合、固定値で `X` を設定すると、画面サイズによってレイアウトが崩れたり、不要なスクロールバーが発生したりする。FlexboxやGrid LayoutのようなモダンなCSSレイアウトを積極的に活用することで、より柔軟でレスポンシブなUIを実現できる。

### 4. ユーザーとのコミュニケーションの重要性
- **教訓**: ユーザーの「正しい」という認識と、コードの「実際の動作」が食い違う場合、安易に自分の分析に固執せず、ユーザーの観察結果を尊重し、その食い違いの原因を徹底的に調査する必要がある。デバッグに必要な情報をユーザーに依頼する際は、なぜその情報が必要なのか、それが問題解決にどう役立つのかを具体的に説明し、協力を仰ぐ姿勢が重要。ユーザーの言葉の裏にある意図や、具体的な状況を深く理解しようと努めること。
## 2026年11月16日 Sticky/予定表 実装の知見

### 1. guard（libs/permission.js）はルール未登録パスをデフォルト拒否する
- **教訓**: 新しいAPIを追加したら RULES / PUBLIC_PATHS への登録が必須。
  ハンドラ直呼びのテストは guard を通らないため検出漏れになる
  （Sticky実装時の403事故）。新API追加時は **guardを通す権限テスト**を必ず書く

### 2. 静的ビルドのフロントはサーバー再起動なしで新しくなる
- **教訓**: dist は静的に配信されるため「UIは新・バックエンドは古」の状態が
  起きうる。「UIは動くのにAPIが403/404」のときは稼働中プロセスの起動時刻を
  確認する（`ps -o pid,ppid,lstart,cmd -p <pid>` + `ss -ltnp`）。
  AIセッションが起動したサーバーは**セッション内で必ず停止する**
  （3011放置サーバー事故。wiki lessons-from-sample-identity.md 関連）

### 3. サンプルデータのオーナーは実ユーザーを使わない
- **教訓**: マニュアル用サンプルデータの主体はテスト表示用ユーザーを作り、
  UPDATEでオーナーを付け替える。実ユーザーの属性（役職員紐付け等）を
  書き換えて見栄えを整えない（全画面の表示を汚染した事故）。
  wiki lessons-from-sample-identity.md 参照

### 4. Sticky（付箋・申し送り）/ 予定表 の構成
- Sticky: Sticky(作者+本文+kind) / StickyStatus(受信者ごと: importance/readAt)。
  kind は宛先の構成から自動判定（他人宛=handoff / 自分のみ=memo）だが、
  明示指定（body.kind）があれば優先。メモを転送すると handoff に昇格
- 予定表: Schedules（会社共有・recurrence monthly/once・dayOfMonth 0=月末・
  末日繰り上げ展開）。カレンダーUIは作らず ICSフィード配信
  （/api/schedule/feed?token= Users.feedToken。展開済み個別VEVENT、
  UID= scheduleId-date@hieronymus）で既存カレンダーから購読する設計
- 予定表の権限: 閲覧 accounting/fiscalBrowsing/administrable、
  編集 accounting/administrable。実績との突合（消し込み）は未実装の次フェーズ
