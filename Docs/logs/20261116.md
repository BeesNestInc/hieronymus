## 予定表（資金繰り予定）機能の実装

### 方針

前々からの要望「月々決まった入出金・資金繰りに影響する入出金の予定表」。
ほとんどの環境には既にグループウェア/カレンダーがあるので、**別系統の
カレンダーシステムを作るのはナンセンス**というユーザーの問題意識から:

- **予定データ（会計データ）は Hieronymus に持つ**。金額・方向・繰り返し
  ルールを持つデータはグループウェアのイベントカレンダーには属さない
- **カレンダー表示はICSフィード配信で既存システムに任せる**
  （Googleカレンダー、Legionカレンダー等どこからでも購読可）
- 月次の一覧はカレンダーグリッドでなく単純な表（月次リスト＋月計）
- 実績（通帳・仕訳）との突合は次フェーズ

ユーザー決定: ICS配信で両対応 / 繰り返し＋単発 / 突合は後回し /
**閲覧も権限限定**（ただし会計閲覧権fiscalBrowsingは「偉い人用の閲覧権限」
という設計意図なので、入出金予定自体の閲覧には含めてよいと確認済み）

### 実装

- **マイグレーション `20261116100000-create-schedules.cjs`**:
  Schedules テーブル（title/kind in,out/amount/recurrence monthly,once/
  dayOfMonth(0=月末・末日繰り上げ)/date/note/enabled）+ Users.feedToken。
  環境差に耐える防御的実装（describeTable確認）
- **`models/schedule.js`**（新規）+ models/index.js・user.js 更新
- **`routes/api_schedule.js`**（新規）:
  - `GET /api/schedule/:year/:month` — 展開済み予定（日付順）+ 月計
    （入金計/出金計/差引）
  - `GET /api/schedule` — 定義一覧 + 自分のフィードトークン
    （**トークン未発行なら初回アクセス時に発行**）
  - `POST /api/schedule` / `PUT|DELETE /api/schedule/:id` — CRUD（バリデーション付き）
  - `POST /api/schedule/token` — トークン再生成（旧トークン失効）
  - `GET /api/schedule/feed?token=xxx` — **ICSフィード（トークン認証）**。
    展開済み個別VEVENT（RRULE不使用。31日→2月28日等の繰り上げをサーバで解決。
    UID=`scheduleId-date@hieronymus` で購読側の重複排除）。終日イベント。
    展開範囲は先月〜12ヶ月後。存在しないトークンは404（列挙防止）。
    失効ユーザーのトークンも404

  編集 `accounting/administrable`。**PUBLIC_PATHS に `GET /schedule/feed`**

  stickyの403事故と同じく必須）。guard通しの権限テストを含める
- **フロント `front/svelte/schedule/schedule.svelte`**（新規）:

## マイページ（カスタムメニュー）の再設計

ユーザーの問い「この機能はみんな便利に使えると思う？便利だとは思うが
わからんと使い辛い」への回答と、「GLM-5.3-Flashが考えた最強のメニュー
システムを思う存分やってみてくれ。ただし他の機能は壊さないで」の指示。

### 調査で判明したこと

- **テンプレートは既に6種類あった**（白紙/ホーム/会計メニュー/顧客管理/
  人事管理/システム管理。Menusテーブル userId=null。
  migration 20250325050712 で config/menu-template.cjs から seed）。
  テンプレート不足が問題ではなく、発見性だけが問題だった
- **/api/menu は permission.js で administrable 限定だった**。
  つまりカスタムメニューは実質管理者専用機能になっていた
  （一般ユーザーは一覧取得すら403）
- **api_menu.js の update/delete に所有権チェックが無かった**。
  権限が開放されると他人のページやテンプレートを壊せる状態

### 実装

- **権限モデルの再設計**:
  - guard: /menu の CRUD を ANY に（全ユーザーがマイページを持てる）。
    /menu/templates GET も ANY。/menu/publish POST は administrable
  - api_menu.js: 所有権チェックを追加（自分のページのみ変更可。
    テンプレートの変更は管理者のみ。他人のページは管理者のみ参照可）。
    **updateでuserId（所有権）を書き換えられないよう保護**
    （テンプレートを個人のページにすり替える・乗っ取り防止）
  - **公開**: POST /api/menu/publish/:id（管理者のみ）。マイページの複製を
    テンプレート(userId=null, displayOrder=max+1)として作る。
    元のページは残る。公開されたテンプレートは全ユーザーの「＋」一覧に現れ
    各自が複製して使う（強制配布ではなく自発的追加）
- **UI**:
  - サイドバー見出し「メニュー」→「マイページ」。鉛筆/＋/✓ボタンにtooltip。
    編集モード中に1行ヒント（「＋からテンプレートで追加。ドラッグで
    並べ替え、×で削除。」）
  - マイページ編集モードに1行ガイド（ドラッグ＆ドロップの手順、
    URLドロップでブックマーク）
  - 実行モードでウィジェット0件のとき empty state 表示
  - 管理者は編集モードで「テンプレートとして公開」ボタン（保存後に表示。
    menu.id 発行後）。公開するとtoastで通知
- **テスト** test/menu.test.js（新規）11件:
  guard通し（CRUDは無権限ユーザーでも可、公開は管理者のみ）、
  所有権（他人のページの参照/更新/削除拒否、テンプレート削除は管理者のみ）、
  userId偽装・所有権書き換えの防止、並べ替えの保護、公開の動作
- **ドキュメント**: documents/menu.md を「マイページ」用語で再構成
  （公開機能の節を追加。画像は既存のものを流用 — サイドバー見出しの
  変更が写る点は許容）。documents/index.md の目次も更新

### 実装中に遭遇した問題

- **テンプレートの隠れた脆弱性**: update/deleteに所有権チェックが無く、
  権限を開放した瞬間に誰でもテンプレートを消せる状態だった。
  権限モデル変更と同時に修正して安全に開放
- **UIのmenuオブジェクトにuserIdが載らない**: serializeMenu/deserializeMenu
  がid/title/displayOrder/widgetsのみを運ぶため、公開ボタンの出し分け条件
  （menu.userId）が常に偽になった。条件を administrable && menu.id に簡素化
  （所有権はAPI側で判定するためUIは.menu.idの有無だけを見る）
- **テストのレース**: api_menu.js のハンドラは非async（.thenチェーン）で、
  `await handler()` が応答完了を待たない。テストヘルパーにポーリング待ちを追加
  （同様の旧式ハンドラをテストするときは同じ工夫が必要）
- **デバッグ用に起動した一時サーバーがnohup起動でも消えることがある**:
  bashツールのセッション終了時にプロセスグループが终止される場合がある模様。
  長時間必要な場合は setsid で完全にデタッチする

### 検証

  （無関係な既存問題）
- build/SSR成功。playwrightで実機確認:
  編集モードのヒント表示、テンプレートからマイページ作成、

- 撮影後、一時サーバー3012停止（3010のみ残存）

## マイページのウィジェットがリサイズできない（ことがある）問題

ユーザー報告「ウィジェットの大きさが変えられない。正確には変えられる時と
そうでない時がある」:

### 原因（3つ重なっていた）

1. **リサイズハンドルが hover 中にしか出ない**（GridStackのautohide）。
   ハンドル非表示中に角を掴むと当然リサイズできない
2. ハンドルは**回転45°のひし形**で、回転の都合上**アイテムの角そのものは
   覆っていない**（ひし形の頂点が角に来るだけ）。角ギリギリを掴むと
   ハンドルを素通しする
3. 角を素通しすると、コンテンツのHTML5ドラッグ（draggable=true。
   実行モード時の「他のマイページへの持ち出し」用）が発火し、
   GridStackのリサイズが始まらない

### 修正

- GridStack.init に `alwaysShowResizeHandle: true` — 編集中はハンドルを
  常時表示（実行モードは resizable無効なのでハンドルは出ないまま）
- 編集中はコンテンツの `draggable` を無効化（GridStackの移動/リサイズに譲る。
  実行モードではHTML5ドラッグ有効のまま）
- ハンドルを 34px に拡大し、`transform: none`（回転解除）＋
  SEハンドルは `right/bottom: -6px` に広げて**グリッドmargin分の隙間も含めて
  角を確実に覆う**

### 検証

## 編集を終える: 自動保存から確認方式へ変更

ユーザーの修正指示「キャンセル終了もありえるので、『忘れるな』でいいんじゃ
ないかな」— 自動保存一本やりだと「キャンセルして破棄したい」需要に応えられない:

- 「編集を終える」時に未保存変更を検出し、確認ダイアログを出す:
  - OK → 保存して終了
  - キャンセル → **破棄して終了**（サーバから最新を再取得して元に戻す）
- 未保存検出は serializeMenu() のスナップショット比較
  （savedSnapshot: 読み込み時・保存完了時に更新）
- 「配置を保存」ボタンは従来どおり（書きながら保存）

### 実装中に遭遇した問題

- **誤検知**: 読み込み直後・未変更なのに必ず「未保存」になる。
  - 原因1: メニュー読み込みのfetchが**2箇所に重複**しており
    （$リアクティブブロックとbeforeUpdate）、実際に走るのは
    スナップショット無しの側だった。loadMenu() に統合
  - 原因2: スナップショットを activateWidgets（ウィジェットのoptions補完）
    の前に取ると、補完値（href等）との差で未保存扱いになる。
    activate後に取る
  - activateWidgets を widget-list.js の共通関数として export
    （components/menu.svelte の initiateWidgets と重複していたロジックを整理）
- 検証: playwright で (1)変更なし終了→ダイアログ無し (2)タイトル変更→
  ダイアログ→保存→反映 (3)タイトル変更→キャンセル→破棄（元タイトルに戻る）
  を確認。テスト 233 passing。一時サーバー停止（3010のみ残存）
