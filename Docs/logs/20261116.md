## 予定表（資金繰り予定）機能の実装

### 方針

前々からの要望「月々決まった入出金・資金繰りに影響する入出金の予定表」。
ほとんどの環境には既にグループウェア/カレンダーがあるので、**別系統の
カレンダーシステムを作るのはナンセンス**というユーザーの問題意識から:

- **予定データ（会計データ）は Hieronymus に持つ**。金額・方向・繰り返し
  ルールを持つデータはグループウェアのイベントカレンダーには属さない
- **カレンダー表示はICSフィード配信で既存システムに任せる**
  （Googleカレンダー、Legionカレンダー等どこからでも購読可）
- 月次の一覧はカレンダーグリッドでなく単純な表（月次リスト＋月計）
- 実績（通帳・仕訳）との突合は次フェーズ

ユーザー決定: ICS配信で両対応 / 繰り返し＋単発 / 突合は後回し /
**閲覧も権限限定**（ただし会計閲覧権fiscalBrowsingは「偉い人用の閲覧権限」
という設計意図なので、入出金予定自体の閲覧には含めてよいと確認済み）

### 実装

- **マイグレーション `20261116100000-create-schedules.cjs`**:
  Schedules テーブル（title/kind in,out/amount/recurrence monthly,once/
  dayOfMonth(0=月末・末日繰り上げ)/date/note/enabled）+ Users.feedToken。
  環境差に耐える防御的実装（describeTable確認）
- **`models/schedule.js`**（新規）+ models/index.js・user.js 更新
- **`routes/api_schedule.js`**（新規）:
  - `GET /api/schedule/:year/:month` — 展開済み予定（日付順）+ 月計
    （入金計/出金計/差引）
  - `GET /api/schedule` — 定義一覧 + 自分のフィードトークン
    （**トークン未発行なら初回アクセス時に発行**）
  - `POST /api/schedule` / `PUT|DELETE /api/schedule/:id` — CRUD（バリデーション付き）
  - `POST /api/schedule/token` — トークン再生成（旧トークン失効）
  - `GET /api/schedule/feed?token=xxx` — **ICSフィード（トークン認証）**。
    展開済み個別VEVENT（RRULE不使用。31日→2月28日等の繰り上げをサーバで解決。
    UID=`scheduleId-date@hieronymus` で購読側の重複排除）。終日イベント。
    展開範囲は先月〜12ヶ月後。存在しないトークンは404（列挙防止）。
    失効ユーザーのトークンも404

  stickyの403事故と同じく必須）。guard通しの権限テストを含める

## マイページのドロップ領域を拡大

ユーザー要望「ページの下にウィジェットを追加する時、すぐに禁止領域になるので
dropできるエリアを拡げて」:

- 原因: drop target（.grid-stack）がコンテンツ（既存ウィジェット）の高さまで
  しか無く、その下はdragoverが受理されずドロップ禁止カーソルになる
- 修正: .grid-stack に min-height: 500px を設定し、既存ウィジェットの下の
  空き領域にもドロップできるようにした（addWidgetはy超過の配置で

- 検証: playwrightで最下部付近へのドロップ→ gs-y 96 に配置されることを

### ドロップが禁止領域になる真因（続き）

min-height だけでは実機で解消しなかった（「ダメだよ。入らないよ」）。
調べると、**dragoverでdropEffectを設定していない**ため:
- ドラッグ元（ウィジェット一覧・サイドバー）が effectAllowed='copy' を
  設定している一方、allowDrop は preventDefault のみ
- Chrome等は dropEffect が 'none' のままだと受け入れ不可（⊘）と判断し、
  **dropイベント自体を発火しない**
- これまでの合成イベントでの検証はドラッグ&ドロップの許可判定を
  バイパスしており、実ドラッグでのみ起こるこの問題を見逃していた

### 合流（merge）の意味づけを整理（同一日に主取引が並ぶケース）

  アンカーとして、直後の同じ日の手数料系の行を吸収する

includeMergeAfter（起票指定の直後合流）も手数料系の行だけを吸収するよう変更。

### サイドバーのhover一時展開をフライアウト（重ね表示）方式に変更

ユーザー指摘の根本原因: hover展開がフロー内で起きるため、別の見出しに
移動した瞬間に前のグループが畳まれて下の見出しが動き、hover先が
外れてしまう（レイアウトシフト）。

hoverだけによる展開（pin/現在地以外）を、下の項目を覆うフライアウト
（position: absolute・背景+影+z-index 1050）に変更。フローの高さが
変わらないので、見出し間を移動しても何も動かない。pin/現在地の
グループは従来どおりフロー内展開（意図的な操作のときだけ動く）。

- flyoutSections/inFlowSections をリアクティブSetで分離
  （Svelte4のテンプレートから関数呼び出しで依存を追跡しない問題への
  対策としてSet参照で渡す）
- ul.flyout は見出し直下（top: 100%）に隣接表示。LI内なので
  見出しからマウスを滑らせて項目に入れる。mouseleaveからの500ms
  遅延閉じはそのまま
- collapsedクラス（マージン調整）は inFlowSections 基準に変更
  （hover展開でも高さが動かないように）

Playwrightで検証: flyout開閉・項目クリックで遷移・表示中の見出しの
位置不変・pinのフロー内展開（flyoutではない）・解除。全30ページの
nav smoke も合格。

操作性のトレードオフ: flyoutが下の見出しを覆う間、その見出しには
hoverできない（flyoutの外に出て閉じる必要がある）。使ってみて
気になるようなら右方向フライアウト方式を検討する。

- ArrowDown/ArrowUpはハイライトを動かすだけ（値は変わらない）
- Enterでハイライト位置を確定、Escapeでリストを閉じる
- 補助科目の候補も同じ形に統一
- ハイライトは入力のたび先頭に戻る

検証: ArrowDown×2で値が変わらない / Enterで確定 / クリックで確定 /

### 学習ルールで直接起票された入金行が計算書と二重起票になる問題を修正

ユーザー報告: 計算書から起票して突合もしたのに、預金通帳の方は
「起票済」で通帳の明細しかない伝票ができた。

原因: 通帳のAmazon入金行が学習済みルール（振込摘要→売上高）で
「借:銀行/貸:売上高」の1行伝票として先に起票されていた（一括起票）。
統合・突合の仕組みは「入金仮」の伝票しか候補にしないため、
計算書側の複合伝票と1行伝票が並び、売上が二重計上される状態になった。

修正:
- 統合候補（findDepositMergeCandidates）を「銀行行だけの1行伝票」まで
  広げる（借:銀行+同額・未承認・1明細・全明細が銀行行に紐付く。
  貸方は入金仮/売上高等の実科目どちらも可。銀行科目・出金仮は除外。
  複数明細の伝票（人の手で組んだもの）は触らない）
- 突合（linkDepositToSettlement）で起票済みの行でも、その伝票が
  銀行行だけの1行伝票なら、その伝票を破棄して計算書側の伝票に
  紐付け替える（rebindBankLineToSettlementDetail）
- 突合候補（suggestSettlementDeposits）に上記の行も含める
  （未照合行に加えて、銀行行だけの1行伝票に紐付く起票済み行）
テスト: 売上高1行伝票への統合/突合による紐付け替え+1行伝票破棄
（全250テスト合格）

### 自動起票ヘルパーの1行伝票の原因（ルールに引っかかっていた）

ユーザー質問: そもそもなんで「銀行行だけの1行伝票」が存在していたんだ？
通帳側では全く起票してないのに。

答え: 計算書の起票時に統合候補が無いと走る自動起票ヘルパー
（bookDepositRowForSettlementSlip）が、bookLinesの通常経路で起票した
ため学習済みルール（振込摘要→売上高。統合時の学習で作られる）に
引っかかり、「借:銀行/貸:売上高」の1行伝票を作っていた。
その当時の統合候補は入金仮しか見なかったので吸収できず放置されていた。

修正: ヘルパーの起票は入金仮を強制する
（bookingsにoppositeAccount: 3900000を渡す。統合される前提の
プレースホルダなのでルールを適用するのは誤り。仮科目なので
学習も汚さない）。
テスト: 学習済みルール（振込→売上高）があっても自動起票は入金仮で
立て、統合後に銀行明細が二重に立たないことを検証（全251テスト合格）。

### 計算書のマッピング（seedDraft）が二重割付する問題を修正

ユーザー報告: 20261116.pdfを読み込ませたら今までのマッピングルールが
摘要されなくなった。

原因2つ:
1. seedDraftの照合で、(摘要,向き)の候補が無いときbyPatternAny
   （向きなしの最初の発生・独立のusedフラグ）にフォールバックして
   いたため、同じ行が複数の行に二重割付された。
   （レイアウトに「FBA手数料」と「FBA 手数料」（空白違い）の重複が
   あると、後者が他の行が使った行をもう一度掴む）
2. レイアウト統合のラベル比較が空白を区別するため、「FBA手数料」と
   「FBA 手数料」が別ラベルとして併存し、さらに古い行には
   学習時の照合バグで「Amazon手数料」のパターンが入っていた
   （ラベルとパターンの不一致）。

修正:
- (摘要,向き)指定の照合は(摘要,向き)のバケットのみから引く
  （byPatternAnyへのフォールバックは旧書式だけに限定）
- レイアウト統合のラベル比較をmakePattern正規化に（空白違いの
  重複を1行に統合。古い壊れたエントリは次回の起票で自然に消える）
- 本番DBで検証: statement 13のseedは二重割付なし（FBA手数料行は
  FBA手数料の行のみに照合）。全252テスト合格。
- 3010はポートを開放（ユーザーが自分で起動するため）
