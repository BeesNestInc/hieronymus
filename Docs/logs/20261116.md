## 予定表（資金繰り予定）機能の実装

### 方針

前々からの要望「月々決まった入出金・資金繰りに影響する入出金の予定表」。
ほとんどの環境には既にグループウェア/カレンダーがあるので、**別系統の
カレンダーシステムを作るのはナンセンス**というユーザーの問題意識から:

- **予定データ（会計データ）は Hieronymus に持つ**。金額・方向・繰り返し
  ルールを持つデータはグループウェアのイベントカレンダーには属さない
- **カレンダー表示はICSフィード配信で既存システムに任せる**
  （Googleカレンダー、Legionカレンダー等どこからでも購読可）
- 月次の一覧はカレンダーグリッドでなく単純な表（月次リスト＋月計）
- 実績（通帳・仕訳）との突合は次フェーズ

ユーザー決定: ICS配信で両対応 / 繰り返し＋単発 / 突合は後回し /
**閲覧も権限限定**（ただし会計閲覧権fiscalBrowsingは「偉い人用の閲覧権限」
という設計意図なので、入出金予定自体の閲覧には含めてよいと確認済み）

### 実装

- **マイグレーション `20261116100000-create-schedules.cjs`**:
  Schedules テーブル（title/kind in,out/amount/recurrence monthly,once/
  dayOfMonth(0=月末・末日繰り上げ)/date/note/enabled）+ Users.feedToken。
  環境差に耐える防御的実装（describeTable確認）
- **`models/schedule.js`**（新規）+ models/index.js・user.js 更新
- **`routes/api_schedule.js`**（新規）:
  - `GET /api/schedule/:year/:month` — 展開済み予定（日付順）+ 月計
    （入金計/出金計/差引）
  - `GET /api/schedule` — 定義一覧 + 自分のフィードトークン
    （**トークン未発行なら初回アクセス時に発行**）
  - `POST /api/schedule` / `PUT|DELETE /api/schedule/:id` — CRUD（バリデーション付き）
  - `POST /api/schedule/token` — トークン再生成（旧トークン失効）
  - `GET /api/schedule/feed?token=xxx` — **ICSフィード（トークン認証）**。
    展開済み個別VEVENT（RRULE不使用。31日→2月28日等の繰り上げをサーバで解決。
    UID=`scheduleId-date@hieronymus` で購読側の重複排除）。終日イベント。
    展開範囲は先月〜12ヶ月後。存在しないトークンは404（列挙防止）。
    失効ユーザーのトークンも404

  stickyの403事故と同じく必須）。guard通しの権限テストを含める

## マイページのドロップ領域を拡大

ユーザー要望「ページの下にウィジェットを追加する時、すぐに禁止領域になるので
dropできるエリアを拡げて」:

- 原因: drop target（.grid-stack）がコンテンツ（既存ウィジェット）の高さまで
  しか無く、その下はdragoverが受理されずドロップ禁止カーソルになる
- 修正: .grid-stack に min-height: 500px を設定し、既存ウィジェットの下の
  空き領域にもドロップできるようにした（addWidgetはy超過の配置で

- 検証: playwrightで最下部付近へのドロップ→ gs-y 96 に配置されることを

### ドロップが禁止領域になる真因（続き）

min-height だけでは実機で解消しなかった（「ダメだよ。入らないよ」）。
調べると、**dragoverでdropEffectを設定していない**ため:
- ドラッグ元（ウィジェット一覧・サイドバー）が effectAllowed='copy' を
  設定している一方、allowDrop は preventDefault のみ
- Chrome等は dropEffect が 'none' のままだと受け入れ不可（⊘）と判断し、
  **dropイベント自体を発火しない**
- これまでの合成イベントでの検証はドラッグ&ドロップの許可判定を
  バイパスしており、実ドラッグでのみ起こるこの問題を見逃していた

74行・日付/内容/出金金額/入金金額/残高/メモ）での検証依頼:

### 原因1: CSVがShift_JIS（既存バグ・修正済み）

- parseCsv が UTF-8 でしか解読しなかった（「銀行直接CSVのSJISは
  要望があれば拡張」とコメントに予告されていた未対応箇所）
- 修正: decodeCsvText — UTF-8解読で置換文字（U+FFFD）が出たら
  iconv-lite で CP932 として再解読（BOM対応含む）
- テスト追加: Shift_JISのCSV解析（235 passing）

### 原因2: 取り込む年度の固定（デザインと案内の問題）

- 取込モーダルは「画面で選んでいる年度」(fy2=2025-08〜2026-07) に
  取込年度を固定する設計（繰り上げ・締め直しの意図）。
  test.csv の行は2026-08以降=第3期の期間 → 74行全部「年度外」で落ちる
- 修正: **全行が年度外で落ちたとき、落ちた行が単一の未確定年度に
  収まっていれば「年度を第n期に切り替えてから取り込んでください」の
  案内警告を出す**（確定済み年度なら確定解除の案内、複数年度に跨るなら
  分割取込の案内）。自動で年度を切り替えるのはしない（驚かせない）
- 過程で試した sizeToContent... ではなく CSV/MIME 判別も修正:
  Windows は .csv に application/vnd.ms-excel を返すことがあり、
  MIMEの excel 判定で xlsx パーサに誤経路していた。
  中身（PK\x03\x04署名）で判別するように修正（2箇所）

### 検証

- node直: parseStatement 74行解析（text/csv / vnd.ms-excel の両MIMEで）
- テスト 235 passing / build 成功
- **サーバー再起動が必要**（decodeCsvText・MIME判別・年度案内は
  バックエンド側）。再起動後に実機で通帳取込→CSVプレビューを確認のこと

### 真犯人: findFiscalYearForTerm のNaN混入（追加修正）

再起動後も「column "nan" does not exist」が残った:
- 取込モーダルは fy=status.fy.term を送る。年度未選択のまま
  通帳取込を開くと status.fy.term が undefined → FormDataで
  'undefined' 文字列化 → サーバの parseInt('undefined') = NaN →
  FiscalYear.findOne の where に NaN が混入 → Sequelizeが
  数値カラムにNaNを素通し → PGが「column "nan" does not exist」
- 修正: libs/fiscal-lock.js の findFiscalYearForTerm で
  parseInt後の有限チェックを追加（解釈不能な年度は年度なし扱い）。
  全呼び出し経路（仕訳・帳票・取込等）がまとめて堅牢化される

### 最終検証

- playwright（最新コードの3012・デバッグ環境）: 通帳取込→test.csv→
  **74行のプレビュー表示**（2026-08-01〜2026-11-13・明細つき）を確認

## 通帳取込（Excel）: 「先にプレビューしてください」エラーの対処

ユーザー報告「Excelを読ませてルールを学習させようとしたら
『プレビューしてないと』のエラー。当然プレビューしてるのに」:

- 起草ルートは「parsed.lines.length === 0」のときこの422を出す。
  プレビューで0行だった可能性が高い=**日付が解析できていない**
- parseDate のコメントに既知のギャップとして明記されていた
  「R6.10.15」「6.10.15」（和暦・短縮年）形式を parseDate に実装
  （令和元年=2019。月日の範囲チェックで非日付の誤検知を防止）
- テスト追加（R6.10.15 / 6.10.15 / 令和6年10月15日 の3形式、
  西暦4桁が従来どおり）: 235 passing
- **ユーザーのExcelファイルで検証が必要**: 違う原因（別の書式）の
  可能性もあるため、test.xlsx等を置いてもらえれば再解析する。
  なお Excelは全期一括の物が来るため、プレビュー/取込の年度フィルタで
  行が落ちる点（「年度外N行」の警告）にも注意
