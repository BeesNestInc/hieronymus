# 2026-11-04: EC計算書の取込（1計算書=1複合伝票）と用語の「通帳」化

## 用語: 口座→通帳（ユーザー決定）

- 動機: EC計算書（Amazon等）を取り込むにあたり、取込対象の一般名が
  「口座」だと計算書が浮く。ユーザーの「通帳」= 外部の相手が発行する
  帳簿を繰り返し書き込んでいく媒体の一般名（家賃帳の例を挙げてもらった。
  銀行の通帳という意味ではない）
- 変更は表示語のみ: メニュー大項目 口座→通帳、口座元帳→通帳元帳、
  取込画面の文案、user向けエラーメッセージ（libs/routes）、documents。
  **内部名（URL/kind値/変数名）は不変**。精算モジュールの「出金元（口座）」
  は財布の意味なので対象外
- 教訓: 命名は実体の構造（fin=口座）とユーザーの語感（通帳）がずれた
  ら、表示語だけを寄せて内部名は放置でいい（URLは固有IDの役割）

## EC計算書の取り込み（ユーザー実例で確定）

- ユーザー実例（20250812.pdf）: 借方 普通預金111,718+広告費1,240+
  支払手数料1,447+広告費8,109+支払手数料55,427 / 買方 売上高177,941
  （税0・売上側合算・1伝票）。この形をそのまま仕様にした
- 計算書=振込1本の内訳書で、カード明細の�像（カード=支出按分、計算書=
  売上+費用按下）。1計算書=1複合伝票。貸借は数学的に必ず一致
- 伝票化の学習: 費用ラベル→科目は計算書の通帳（financial）単位の
  学習ルールに蓄積（BankStatementRule流用。新規機構なし）
- 通帳側: Amazon振込行は**複合伝票の預金明細と直接紐付け**（matched）。
  伝票2枚目を作らない=二重計上を防ぐ。bankBoundの判定で計算書側行と
  通帳側行が同じ明細detailsを共有する特殊形（既存のusedIds不変なのは
  自動突合のみ）。候補選択は daydiff → slip id新しい方（テストが
  同額の複数計算書で同額を踏んだ）
- 注意: 複合伝票の預金行・費用行は「片脚0/null」の明細（createCrossSlip
  で学習が銀行脚101だけ走る=誤学習しないことを学習の実装で確認済み）
- 教訓1: 片脚ある行の表現は既存の伝票入力と同じ多借多貸でOK
  （借方or貸方の片方0.合佫は行合計で一致させる）
- 教訓2: テストの途中生成で半端（amountIn amountOut両方ある行）に
  なると分解が変わる。fixture上書きを最小にする

## 振込行の読み取りの安定化（実機検証）

- 実データ（20250729.pdf）で通し確認したところ、AI読取の揺れが2種出た:
  1. 振込行のラベルが「純利益」だけに切れる（「振込」が落ちる）→
     既定の振込語 '振込' では特定できない
  2. 振込行そのものが配列から欠ける（計算書の最終行を見落とす）
- 対策:
  - 振込行の既定語を '振込|純利益' に（計算書分類と通帳候補で共有定数）
  - STATEMENT_PROMPTに「計算書では最後の振込行も必ず1行として出力」を追加
- 修復後の実機: 9行・売上141768=振込38268+費用103500・警告0 を再現
- なおAI読取は行集合の再現性が完全ではない（同一ファイルで行数のゆれが
  観測されたことがある）。**検算ガード（合わないと起票不可）があるため
  壊れた読みで仕訳は組めない**。悪読取時は警告で分かり、再取り込みで
  回復する。読み取り安定化はプロファイル起草の CSV/TSV 取込（決定的解析）
  が根本解決の位置にいる
- 教訓: **AI読取を含むextractは「行集合」での検証（合ってるかを合計で）
  を必ず挟む**。行単位の正しさはLLMの偶然に依存するので、合計の紐付け
  （借方合計=貸方合計）を規約に組み込むのが定石

## 実際のデータで分かった約束科目（ユーザーの台帳）

- 売上高(6000000) 補助1=Amazon 補助2=Orcinus / 支払手数料(7030110)

  普通預金(1010010) 補助1=住信SBI 補助2=島根中央信用金庫
- ユーザー例の「広告費 (プロモーション割引額)」「支払手数料 (FBA)」の

  （oppositeSubAccount。findLearnedRule/学習ルールは補助対応済み）
- config/banks/Amazon.yaml を作成（received/saleの約束科目を持ち、
  伝票化パネルの初期値になる。費用行は学習ルールにおまかせ）
- fin作成の勘定科目は settlement では必須としない（改修済み。
  KINDSにsettlementを入れて、cleanInputのnull化も直した）

## 計算書の通帳は科目を持たない（ユーザー指摘）

- 指摘: 通帳作成で科目が必須。でも計算書は「金の動きが銀行通帳側で
  済んでいる帳簿」であって金を持たない。科目を要求するのは当然おかしい
- 改修: fin作成（UI/サーバどちらも）で settlement は勘定科目を出さず
  nullで登録。メモ保存の「科目を選択してください」の残骸も撤去
- 教訓: **取り込み対象の帳簿（通帳）に二種ある**: 金の出入りが記載される
  帳簿（通帳・カード=勘定科目を持つ）と、金はない内訳書（計算書=
  勘定科目を持たない。入金先・費用は伝票化のときに決める）。この
  区別をデータモデルで持った（kind: settlement は accountCode null）

## 読み取れない（ユーザー報告）→ 8月計算書はテキスト層が読める

- 報告: 計算書の取込で「読み取れない」。20250812.pdfを調査すると
  **テキスト層が読める**支払明細書だった。カード明細パーサが振込説明の
  文章1行だけ拾ってしまい（lines.length!==0）、AIフォールバックが
  発火しない罠に落ちていた
- 対策: 支払明細書シグネチャ（支払明細書+純利益）のあるPDFは
  parseSettlementTextLinesで決定的に解析する（AI不要・無料）。
  テキスト層のない7月型は従来どおりAI読取
- 構造の発見: Amazon支払明細書は**入れ子**（支出66,223 = プロモ1,240 +
  FBA1,447(=納品895+在庫552) + 広告8,109 + Amazon55,427）。集計行と
  内訳が両方載るので全行選択だと検算が合わない。**費用行にinclude指定**
  （伝票化パネルのチェックボックス）を追加: 選択合計で検算が合うときだけ
  起票できる。ユーザーの仕訳例（1,240/1,447/8,109/55,427）は
  集計行を選んだ形に一致する
- salePatternは指定時だけ厳格判定に変更（省略時「振込以外の入金=売上」）。
  AI読取で「売上」接頭辞が落ちることがあるため（Amazon.yamlからも外した）
- 教訓1: **テキスト層があるPDFでも、拾える行が少ないとカードパーサが
  誤発動する**。書式シグネチャによる経路分け（支払明細書→計算書パーサ）
  が正解。lines.length===0だけがフォールバックの引き金では足りない
- 教訓2: 明細書の合計行と内訳行は入れ子。**集計と内訳の同時掲載**は
  「全行を採用しない」前提の設計（選択+検算ゲート）で受ける

## 個別対応にならないか（ユーザー指摘）→ プロファイル駆動に改修

- 指摘: 計算書のテキスト解析がAmazon専用コードになったら、次のモールで
  また個別対応（コード変更）になって困る
- 改修: parseSettlementTextLinesをプロファイル駆動に。書式の語彙
  （detect/aggregateSale/aggregateExpense/transferPattern/
  transferDatePattern/memoPattern）はすべて config/banks/*.yaml に。
  **コードには「支払明細書系の文法」（ラベル+￥額の行構造）だけ**。
  新しいモール=新しいyaml（テストで楽天風の架空書式をyamlだけで
  解析できることを証明した）
- 決定的解析の判定もプロファイルのdetectで行う（AI読取専用の
  settlementプロファイル=detectなし、も可能）
- 未知の書式の保険: PDFの明細行が2行未満ならAI読取に譲る一般ゲート
  （カードパーサが振込説明文だけ拾う罠の一般化。7月=字形PDF、
  8月=テキスト層あり、の両方が通る）
- バグ修復: YAMLの単一引用符内の \\d はリテラルのバックスラッシュ2つに
  なる（正規表現が壊れる）。**YAMLで正規表現を書くときは単一引用符+ \ 一つ**
- 教訓: **「書式の差はプロファイル、文法はコード」の分離を最初から**。
  Amazon専用の正規表現をコードに置いた時点で「次のモール問題」が
  起こる。diffを見てyamlに移せる形に直す習慣

  全体スクロールという安易な解だった

## フッタ問題の真意（ユーザー再訂正）→ メインの伸び

- 指摘の真意: フッタが「大きい」のではなく**メインコンテンツが短い**
  （内容の少ないページでメインが伸びず、フッタの上が空く/フッタが
  画面内に入ってこない）
- 修正: bodyをflex columnに（ヘッダ+メイン+フッタ）。content-wrapperを
  flex:1にして残りを埋める→フッタは常に画面下端。フッタ自体の
  コンパクト化は前回のまま有効
- 教訓: 「フッタが大きい」は言葉のまま取らない。**画面の占有率の話**
  （どの領域がどれだけあるべきか）を図で確認してから直す
