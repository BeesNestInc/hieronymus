### 棚卸し（自動抽出スクリプトによる実測）

## 一般従業員ケースのシナリオテスト（続き）

「ケースを考えてテストしよう」より、一般従業員（権限なし）の4つの保証を
通しのシナリオで検証した（test/employee-case.test.js・34テスト）:

1. 機微なデータにはアクセスできない — 日記帳/元帳/残高/試算表/推移表/
   学習ルール/口座一覧/ユーザー一覧/年度変更/取込起票/伝票作成・更新は
   guardで拒否。他人のユーザー情報はhandlerで拒否。通帳一覧は自分の
   個人カードだけ
2. 自分の関係するデータの投入はできる — 証憑登録・浮遊ファイルの
   アップロード・精算書の作成・未整理証憑パイル
3. 自分の投入したデータを操作できる — 証憑の更新・bind・ファイル追加・
   ファイル削除、精算書の更新、明細への証憑割り当て
4. 承認処理をされた後は操作できない — 精算書の更新・削除は拒否（-2）。
   承認で起票された伝票は削除も更新もできない

### ケース4で見つかった穴（修正済み）

承認済みの精算書の明細に載った証憑を、作成者本人がその後も更新・削除・
ファイル操作できていた（承認済み伝票の明細はその証憑を指しているのに）。
→ `voucherInApprovedReport` チェックを追加（api_voucher.js）。
証憑の更新・削除・upload・bind・deleteFileで、承認済み精算書に載っている
証憑は会計権限なしには操作できない。会計権限は従来どおり操作可
（経理は伝票も直せるので）。

### 結果（追試込み）

- 全338テスト合格（304 → 338）

## 経理部員ケースのシナリオテスト（続き2）

「部員は全経理データを参照できる / 全伝票と証憑の投入・修正・削除が
できるが承認はできない / 承認後は関係データを一切操作できない」を原則に
演繹して検証した（test/accounting-case.test.js・22テスト。

### 原則の演繹: 承認済みデータの変更可否は「承認権限」で決める

一般従業員ケースでは承認済み精算書の証憑ガードを「会計権限なら可」に
していたが、これは経理部員（会計権限・承認権限なし）では成り立たない。
不承認に戻せるのは承認権限だけなので、**承認済みデータに関わる変更は
承認権限に限る**が正しい。修正:

- `voucherInApprovedReport` → `voucherInApprovedData`:
  - ガード条件を !会計権限 → **!承認権限** に（作成者・会計権限でも不可）
  - 参照先に**承認済み伝票の明細**（伝票ビューで証憑を直接紐付けた場合の
    debitVoucherId/creditVoucherId）も追加。承認済み精算書の明細経由しか
    守れていなかった

### そのほか見つかったもの

- 伝票の削除が「承認権限 or 作成者」限定だった → **会計権限も許可**
  （原則: 全伝票の削除ができる。承認済みは従来どおり-2で全員拒否）
- 不承認API（PUT /cross_slip/approve の approvedAt: false）が
  DATE列にfalseを直接入れようとして保存に失敗した → `|| null` で正規化
  （フロントはnullを送るので実害なし。頑健化）
- test/ai-memory.test.js にsuite間の接続プール再初期化パターンを追加
  （accounting-case がsuite中で最初にpoolをcloseするようになったため）

### ケースの内容（test/accounting-case.test.js）

1. 全経理データ参照: 会計帳簿一式、日記帳・証憑一覧・精算書一覧に他人の
   データが出る、通帳一覧に銀行口座が出る（従業員には出ない）。
   ただしユーザー情報（人事データ）は参照不可
2. 投入/修正/削除・承認不可: 伝票の新規起票（未承認で入る）、他人の
   未承認伝票の修正・削除、他人の証憑の修正・削除、伝票・精算書の
   承認不可、年度確定可（取り消しは管理権限）
3. 承認後: 承認済み伝票の更新・削除不可、承認済み伝票が参照する
   **自分の**証憑も更新・削除不可（承認権限なら可）。
   不承認に戻すと経理部員も再び操作できる（凍結は承認に束ねられている）

## 年度の確定を管理権限のみに限定（ユーザー指摘）

「一般部員（会計権限）が年度確定できるのはマズくないか」との指摘。

確定は全データを不変にするコミット操作で、取り消しは管理権限のみに
対称性が取れていない（会計が押せば管理権限の出番を強制する）。
確定は承認の類ですらない（もっと上の締め操作）ので、取消しと同じく
**管理権限のみ**に限定した:

- libs/permission.js: `/term/:id/lock` を accounting+administrable →
  **administrableのみ**に
- front（home/widgets両term.svelte）: 「確定」ボタンを管理権限のみに表示
- テスト: 権限マトリクス3件追加、経理部員ケースは「確定も不可」に変更、
  従業員ケースの機微リストに年度確定を追加

### 結果（年度確定込み）

- 全364テスト合格（360 → 364）

### 人事閲覧権限（personnelBrowsing）の新設

「人事情報の参照」の実現が問題になった。人事管理権限
（personnelManagement）は/member読み書きと/usersのセット権限で、
経理デスクに付与すると人事操作もできてしまいspecに反する。
会計閲覧権（fiscalBrowsing）と同じ構成の**閲覧専用フラグ**を新設した
（ユーザー決定）:

- マイグレーション 20261122100000: Users.personnelBrowsing
  （test/dev/productionの3DBに適用済み）
- 許可表: GET /member・GET /users に人事閲覧権を追加。
  POST/PUT/DELETEは従来どおり人事管理権限・管理者のみ
- GET /user/:idのnarrowingに人事閲覧権を追加
- ユーザー一覧画面に「人事閲覧」チェックボックスを追加
- 役職員管理ページ: authorityに人事閲覧権を追加（参照のみ開放）。
  「役職員入力」ボタン・保存・削除ボタンは人事管理権限・管理者のみ表示
- 経理デスクのフラグ構成: 会計+承認+顧客管理+人事閲覧
  （管理・人事管理・AI管理・在庫管理は持たない）
