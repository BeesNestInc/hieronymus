## 一般従業員ケースのシナリオテスト（続き）

「ケースを考えてテストしよう」より、一般従業員（権限なし）の4つの保証を
通しのシナリオで検証した（test/employee-case.test.js・34テスト）:

1. 機微なデータにはアクセスできない — 日記帳/元帳/残高/試算表/推移表/
   学習ルール/口座一覧/ユーザー一覧/年度変更/取込起票/伝票作成・更新は
   guardで拒否。他人のユーザー情報はhandlerで拒否。通帳一覧は自分の
   個人カードだけ
2. 自分の関係するデータの投入はできる — 証憑登録・浮遊ファイルの
   アップロード・精算書の作成・未整理証憑パイル
3. 自分の投入したデータを操作できる — 証憑の更新・bind・ファイル追加・
   ファイル削除、精算書の更新、明細への証憑割り当て
4. 承認処理をされた後は操作できない — 精算書の更新・削除は拒否（-2）。
   承認で起票された伝票は削除も更新もできない

### ケース4で見つかった穴（修正済み）

→ `voucherInApprovedReport` チェックを追加（api_voucher.js）。

証憑は会計権限なしには操作できない。会計権限は従来どおり操作可
（経理は伝票も直せるので）。

## 担当者選択の穴（ユーザー指摘）と案件集計の仕様確認（続き5）

## 管理者ケースのシナリオテスト（続き6）

管理者（administrableのみ）の原則:
「管理者」としてできるのは**ユーザー権限の操作**だけで、個々の具体的な
操作（会計・承認・取込・AI設定・顧客管理の実務）はできない。
現実には自分に権限を与えればできるが、それは権限操作経由。

### 検証結果 — 原則は現行実装で全うされていた（コード修正なし）

1. ユーザー権限操作: /users・他人のユーザー情報・他人の権限変更・
   ユーザー削除ができる（実ハンドラで使い捨てユーザーの権限付与・
   削除を検証）
2. 個別操作は不可: 会計帳簿・伝票一式・取込・突合・学習ルール・口座・
   顧客管理の実務（companyManagementが必要）・AI設定・プロンプト
   （管理領域でもaiManageが必要）— 全て拒否
3. 対比のピン: 年度の**内容変更**（税込み等）は会計、**確定/取り消し**は
   管理権限 — 権限の分離が設計どおり
4. 証憑一覧・精算書一覧は自分の分だけ（narrowingが効いている）
5. 抜け道の実証: 自分に会計権限を与えれば（権限操作として正当に）
   会計ができるようになる経路をテストで確認

### 設計として残る知見

- **役職員マスタ（/member）は管理者も直接操作できる**: 人事管理権限の
  上位互換の設計。ユーザーとの紐付け（誰がどのユーザーか）が役職員情報に
  含まれるため、管理者が管理対象にしている。「管理者はユーザー権限操作
  だけ」と読むなら外すこともできるが、ユーザー管理と役職員管理は
  一体的に運用するのが自然と判断し現状維持

→ **ユーザー判断: 分離する**。管理者（administrable単体）は役職員マスタを
直接操作できないようにした（続き7）:

- 許可表: GET /member → 人事管理・人事閲覧のみ、書き込み → 人事管理のみ
  （administrableを除去）
- 役職員管理ページのauthorityから管理者を除去。入力・保存・削除ボタンの
  条件も人事管理権限のみに
- 管理者が役職員を扱うときは人事管理権限を（自分に）与える経路になる
  （「現実には自分に操作権を与えればできる」の原則どおり）
- テスト: 管理者ケースを「直接はできない」に修正、権限マトリクスに
  人事管理権限の許可2件と管理者の拒否1件を追加

### 結果（役職員の分離込み）

- 全425テスト合格（422 → 425）

## 設問「mitaniは自分が書いた伝票で承認済みのものを削除する方法はあるか」

本番のmitaniは 会計権限のみ（承認権限なし・485件の承認済み伝票）。
全削除経路を検証した:

1. 直接削除（DELETE /cross_slip）: 承認ガード（-2）が権限チェックより
   **先に**効く。全員（承認権限者も）拒否
2. 不承認に戻してから削除: 不承認（PUT /cross_slip/approve）には
   **承認権限が必要** → mitaniは不可
3. 経費精算経由（DELETE /expense_report/slip）: 許可表が承認権限のみ、
   handlerも承認済みは会計権限併用 → mitaniは不可
4. 取込の再実行・「起票をやめる」・unsettle: すべてapprovedAtガード済み

**結論: mitaniに承認済み伝票を削除する方法は無い。** 削除できるのは
承認権限者（不承認→削除の2段階）。経費紐付伝票は承認権限+会計の
ユーザー（ogochan）のみ。mitaniの実務上の出口は、承認者に不承認と
削除（または修正）を頼むこと。

### 検証中に見つけた隣接の穴（修正済み）

PUT /cross-slip-detail（明細単位更新・許可表は会計権限）に承認チェックが
無く、会計権限なら**承認済み伝票の明細を直接書き換えられていた**。
本体更新は-2で全員拒否するのに明細だけ素通りする状態
（フロント未使用の経路）。本体と同じく承認済みは-2で全員拒否に揃えた。
テスト: 経理部員ケースに明細単位更新の拒否を追加。
